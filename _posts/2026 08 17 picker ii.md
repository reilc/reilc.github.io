## The Challenge

> Can you figure out how this program works to get the flag?
>
> Connect to the program with netcat:
> ```
> $ nc saturn.picoctf.net 51918
> ```

The program's source (`picker-II.py`) was also provided. Stripped down, the
relevant logic is:

```python
def win():
  flag = open('flag.txt', 'r').read()
  flag = flag.strip()
  str_flag = ''
  for c in flag:
    str_flag += str(hex(ord(c))) + ' '
  print(str_flag)

def filter(user_input):
  if 'win' in user_input:
    return False
  return True

while(True):
  try:
    user_input = input('==> ')
    if( filter(user_input) ):
      eval(user_input + '()')
    else:
      print('Illegal input')
  except Exception as e:
    print(e)
    break
```

So the program reads a line of input, checks it against `filter()`, and if
it passes, appends `()` to it and hands the whole thing to `eval()`. The
`win()` function reads `flag.txt` and prints it out as space-separated hex
byte values. Getting the flag means getting `win()` to execute — but the
filter blocks any input containing the literal substring `win`.

The hint pointed at this directly: *"Can you do what `win` does with your
input to the program?"*

## Initial Approach

My first instinct was that if I couldn't type `win` directly, I could
probably encode it and let `eval()` decode it back into the real string at
runtime. I tried a few variations:

- `\x77\x69\x6e`
- `0x77 0x69 0x6e`
- `bytes.fromhex('77696e').decode('utf-8')`

None of these worked — every attempt threw `'str' object is not callable`.

The reason, once I worked through it: `filter()` only ever sees the raw
text I typed, so none of these tripped it (no literal `win` substring
appears in `\x77\x69\x6e`). But once `eval()` actually *parses* that text as
Python code, the escape sequences get decoded into the real string `"win"`
before anything else happens. So what I was actually asking Python to run
was:

```python
eval("'win'()")
```

That's the string `'win'` immediately followed by a call `()` — and you
can't call a string. I'd successfully smuggled the *text* `win` past the
filter, but I still ended up with a string object, not the function.

## The Vulnerability / Concept

The real gap in this challenge isn't in `eval()` itself — it's that
`filter()` only ever inspects the literal characters you send it. It has no
way to reason about what those characters *resolve to* once executed. As
long as the raw input never contains the three characters `w`, `i`, `n` in a
row, the filter is satisfied, no matter what object that input ends up
referring to at runtime.

That gap is exploitable because Python functions are first-class objects —
same type category as an `int` or a `list` — not something a language
grants special, unreachable status. `globals()` is just a `dict` mapping
every name in the global namespace to whatever object it points to,
including `win` itself. That means the *object* `win` refers to can be
reached through a completely different, filter-safe path:

```python
list(globals().values())[13]
```

This indexes into the *values* of `globals()` rather than the *keys*, which
means you get the actual function object sitting in memory — not the string
`"win"`. Appending `()` to that expression calls it directly:

```python
eval("list(globals().values())[13]()")
```

None of the characters `w`, `i`, `n` appear together anywhere in that
string, so `filter()` passes it straight through. But once `eval()`
executes it, index `13` resolves to the real `win` function object (dict
ordering is stable in Python 3.7+, so the same index lines up consistently
between `.keys()` and `.values()`), and `()` invokes it — functionally
identical to typing `win()`, just reached by object reference instead of by
name.

## Solution

Connect to the challenge with netcat:

```
$ nc saturn.picoctf.net 51918
```

At the `==>` prompt, first confirm which index in `globals()` holds `win`
(I checked with `.keys()` first, which prints the *name* `win` — that
attempt still gets blocked as `'str' object is not callable` if called, but
confirms the index):

```
==> list(globals().keys())[13]
```

Then call the same index from `.values()` instead, which is the actual
function object:

```
==> list(globals().values())[13]()
```

This returns the flag, printed as space-separated hex byte values (that
hex formatting is `win()`'s own doing — see below).

## Solution From the Answer Key

The official solution module gave a different, more direct path:

```python
print(open('flag.txt', 'r').read())#
```

Sent as input, the full string `eval()` executes becomes:

```python
eval("print(open('flag.txt', 'r').read())#()")
```

**What the trailing `()` does:** nothing — because `#` starts a Python
comment, and comments run to the end of the line unconditionally. The
appended `()` is never parsed as code at all; it's simply text after the
comment marker, discarded before execution even begins. This directly
defeats the assumption baked into `eval(user_input + '()')`, that user input
is always a bare expression needing a trailing call.

**Why the flag prints as plain text instead of hex:** this solution never
touches `win()` at all. It opens and reads `flag.txt` directly with
`open(...).read()` and prints the raw contents — no transformation applied.
The hex-encoding I saw in my own solution isn't something Python or `eval()`
does automatically to flags; it's a deliberate design choice inside `win()`
specifically:

```python
for c in flag:
    str_flag += str(hex(ord(c))) + ' '
```

Since `flag.txt` is just a file on disk, any code with file-read access can
retrieve its contents — you don't need to reach `win()` specifically to get
the flag, you just need `eval()` to run *some* code that reads the file.

## What I'd Do Differently

- The `#` comment trick is the more elegant solution — it sidesteps the
  filter-bypass puzzle almost entirely by breaking the assumption the
  challenge's `eval(user_input + '()')` line makes, rather than working
  around the filter's string matching. It's a good reminder to look for
  weaknesses in how input gets *concatenated and parsed*, not just what
  the blacklist checks for.
- Going forward, when I see a blacklist filtering on substrings, I want to
  think earlier about: (1) can I reach the same object through indirection
  (`globals()`, attributes, etc.), and (2) can I terminate the parser early
  (comments, statement separators) so injected boilerplate around my input
  never executes.
- Worth reviewing: Python's `#` comment behavior more broadly, and other
  common ways trailing/leading code gets neutralized in injection-style
  challenges (e.g. `;`, multi-line strings).

## Key Takeaway

Functions in Python are first-class objects, not special reserved names —
they live in `globals()` like any other value, and can be retrieved,
passed around, and called without ever referencing them by their literal
name. A filter that only checks input *text* has no visibility into what
that text resolves to once it's actually executed, and that mismatch
(text-level filtering vs. runtime object resolution) is the core lesson of
this challenge.
