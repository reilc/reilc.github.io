Buffer Overflow 1

picoCTF • Binary Exploitation • Medium

Challenge Info

  • Platform: picoCTF
  • Category: Binary Exploitation
  • Difficulty: Medium
  • Points: -
  • Tools used: VS Code (for viewing source code), GDB

Goal

overflow buf with an exploit string so that the vuln function gets called

The relevant logic from the challenge is: 


                #define BUFSIZE 32
                #define FLAGSIZE 64

                void win() {
	                char buf[FLAGSIZE];
	                FILE *f = fopen("flag.txt","r");
	                if (f == NULL) {
		                printf("%s %s", "Please create 'flag.txt' in this directory with your",
			                "own debugging flag.\n");
			   
		                exit(0);
	                }

	                fgets(buf,FLAGSIZE,f);
	                printf(buf);
                }

                void vuln(){
	                char buf[BUFSIZE];
	                gets(buf);
	                printf("Okay, time to return... Fingers Crossed... Jumping to 0x%x\n", get_return_address());
                }

                int main(int argc, char **argv){
                	setvbuf(stdout, NULL, _IONBF, 0);
	
	                gid_t gid = getegid();
	                setresgid(gid, gid, gid);
	
                	puts("Please enter your string: ");
                	vuln();
	                return 0;
                }

Attempts

First Attempt

I wanted to find out what get_return_address is as it might be a clue as to how we can call win. After looking it up online, I learned that it's a custom function that reports the address that the CPU will jump to when the current function executes ret or returns instruction back to the caller function.

From here, my next step was to try overwriting the address held at that function to be the address of win. That meant that I'd also have to find the address of buf which was too difficult. Thus, I went to try a different angle.

Second Attempt

After looking at the hints, I learned that I needed to change vuln's return address to be win's address.

I started by finding win's address by going into GDB and creating a breakpoint, giving me 0x80491fe. Next, I thought about how to create the exploit string. I knew buf was 32 bytes, but I still had to find out where it started so that I could take into account where saved ebp and the return address were.

After meticulous GDB work, I finally found that buf started at 0xfff821c0. From there, I used GDB to examine the segment of memory starting from the buffer to the return address. I noticed that after the buffer, there was an 8 byte gap until saved ebp (which itself is 4 bytes). The next 4 bytes after saved ebp was the return address, which is also 4 bytes. So, taking all of this into account, my attack string needed to be 48 bytes long (32 + 8 + 4 + 4), with the last 4 bytes being the address of win.

I created my exploit string, which consisted of 44 A's followed by the target address written in reverse, since this is in little endian. I entered my string into the program and, unfortunately, got a segmentation fault back.

Solution

The solution picks up on where my second attempt leaves off. The issue was that the address I found for win was incorrect, as using breakpoints to find an address isn't exactly the right way to do this.

Instead, the correct way would've been to use print win or disas win and either read the return value or read the very beginning of the disassembly. As it turns out, win's actual address was 0x084091f6, a few bytes before the previous address I found.

The segmentation fault occurred because the CPU was executing intstructions without win's frame being established beforehand. So when win does its ebp relative stack addresses, it does them in the wrong area of memory.

The reason why creating a breakpoint at win gave a different address was because GDB uses "prologue skipping", meaning it analyzes the function's opening instructions (push ebp, mov ebp, esp, etc...), recognizes them as boilerplate setup, and places the breakpoint right after it because after the setup is where the function's "real logic" begins. 


                0x080491f6 <+0>:    endbr32
                0x080491fa <+4>:    push   ebp
                0x080491fb <+5>:    mov    ebp,esp
                0x080491fd <+7>:    push   ebx
                0x080491fe <+8>:    sub    esp,0x54      ← b win landed here

Afterthoughts

I feel silly for blindly believing that i had the right address even after seeing that the disassembly didn't quite match up. To be honest, I didn't think the addresses before 0x080491fe really mattered too much (I was too focused on determining if my exploit string was wrong or if I forgot to take another factor into account) so I paid no attention to them. I did have a hunch that the address I was using should've been 0x080491f6, but I didn't take that hunch seriously. I guess that goes to show that trusting your gut can help and that trying something for the sake of trying it doesn't hurt (especially for a problem like this).

fortunately, i had already done most of the heavy lifting with finding where my buffer began and writing my exploit string, so fixing up the address wasn't too bad. still is frustrating being so close to the answer and not realizing it until late.
