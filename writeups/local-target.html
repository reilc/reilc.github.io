Local Target

picoCTF • Reverse Engineering • Medium

Challenge Info

  • Platform: picoCTF
  • Category: Reverse Engineering
  • Difficulty: Medium
  • Points: -
  • Tools used: VS Code (for viewing source code), GDB

Goal

Get the following program to print out the flag by overflowing the buffer to overwrite a local variable, num. By assigning num the value, 65, a conditional check is passed and the flag is printed out.

The relevant logic from the challenge is: 


int main() {
	FILE *fptr;
	char c;

	char input[16];
	int num = 64;
	printf("Enter a string: ");
	fflush(stdout);
	gets(input);
	printf("\n");
	printf("num is %d\n", num);
	fflush(stdout);

	if( num == 65 ) {
		printf("You win!\n");
		fflush(stdout);

		// Open file
		fptr = fopen("flag.txt", "r");
		if (fptr == NULL) {
		    printf("Cannot open file.\n");
			fflush(stdout);
			exit(0);
		}

		// Read contents from file
		c = fgetc(fptr);
		while (c != EOF) {
			printf ("%c", c);
			c = fgetc(fptr);
		}

		fflush(stdout);
		printf("\n");
		fflush(stdout);
		fclose(fptr);
		exit(0);
	}

	printf("Bye!\n");
	fflush(stdout);
}

Approach -> Solution

From viewing the source code, I saw that my input went into input- a char array. I know it holds 16 bytes because a char is one byte in C. gets is an unsafe C function because it doesn't check how many bytes it writes into memory. So, if my input is long enough, I could overwrite memory addresses I shouldn't be able to. For this problem, I want to overwrite num to change its value.

To go about changing the value of num, I first had to find where num is in memory. Fortunately, this wasn't too difficult to find. By running the program in GDB and looking at the disassembly of the main function, I could clearly see where num was being assigned: 


                0x0000000000401242 <+12>:    mov    DWORD PTR [rbp-0x8],0x40

I knew this was num because the value 0x40, which is hexadecimal for the number, 64, is being assigned to some address below rbp (base pointer register). Now that I knew which address to reach, which was 0x7fff03164b78, I had to now find out where my input starts from so I can build my attack string.

In the C source code for the program, I saw that input is declared and assigned before num, so I figured that my input would start at at some address lower than 0x7fff03164b78. Since input is 16 bytes in size, I subtracted 0x7fff03164b78 by 0x10 (the hex representation of 16) and examined the bytes there. I noticed an area of 0x00 bytes which seemed to belong to input.

I took the address of where the 0x00 bytes started and reran GDB with an input of 16 A's. I reexamined the address and noticed that the 0x00 bytes were now 0x41 bytes, showing me exactly the memory area of input (0x41 is hexadecimal for A). With this, I could now work on my attack string.

Using a hex calculator I found that the distance from num to input was 24 bytes. This meant that my string would be 25 characters long- 24 characters to reach num and the last character being the value I want num to be. To get the flag, num had to be 65 (decimal value). Coincidentally (or maybe intentionally according to the challenge author), the hexadecimal for 65 is 0x41 which as I saw earlier is the same representation for the character 'A'. This meant that my attack string could be 25 A's (or any combination of letters really, as long as 'A' is the last).

I entered my string in the progam and got back the flag.

Afterthoughts

I thought my solution was good until I later noticed that the rsp register (at some point in the program) contained the same address as where input starts. When I looked back at my notes on registers, this made sense because (according to my notes from the picoCTF primer): rsp "Shows where the top of the stack is. Creating a local variable moves this pointer so that it can make space for it. For example, creating an int variable that takes 4 bytes moves the stack pointer 4 bytes."

So if I had remembered how rsp behaves, I could've saved myself some time and brain power. But at least now, going forward, I can be more aware of that fact in future CTFs.
